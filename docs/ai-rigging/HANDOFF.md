> 把 MotionForge 这边的现状、操作流程、技术判断写成一份，丢给正在研究 AI 打关节的另一个 chat，避免对方从零拼背景。

---

## 1. 项目背景

**MotionForge** 是一个 Web 3D 动作编辑器（Three.js + Vite）。用户加载模型（GLB/USD/FBX），给零件配关节（铰链/滑轨），然后用自然语言或关键帧驱动模型做动画，最后导出标准化运动包（ZIP）。

**端到端已经 work**：加载 → 配关节 → 自然语言生成参数化公式（AI 生 PKF） → 动画播放 → 导出/导入。

**唯一卡门槛的步骤**：手动配关节。这一步需要用户懂机械运动学，外行做不了。我们想用 AI 替代这一步，其他保持不动。

### ⚠️ 重要：我们的模型分布特点（直接影响你的技术路线）

我们的目标场景是**工业 AGV / 叉车 / 物流机器人**，实际关节分布：

- **80%+ 是 prismatic（平移）关节**：门架升降、车体前进、叉齿侧移、叉齿前伸……
- **少量 revolute（旋转）关节**：偶尔出现（比如叉齿倾斜）
- **极少 fixed 关节**

这个分布的技术含义：
- **prismatic 的 origin 不参与计算**（MotionForge 数学公式决定的，见第 3 节）→ origin 精度对我们**基本无关**
- **父子拓扑**每个关节都需要，是**实际最关键的评估维度**
- **revolute origin 精确定位**长期重要（是技术基础），但**不是当前第一优先级**

所以：
- **研究重心要前移到"父子拓扑 + prismatic axis 判断"**
- **revolute origin（圆柱面拟合等几何算法）继续研究作为基础**，但不必为当前阶段赶工

## 2. 当前"配关节"操作流程（要替代的那一步）

用户在左侧场景树选中一个零件，打开关节配置面板，手动填：

| 字段 | 含义 | 可选值 |
|---|---|---|
| **type** | 关节类型 | `revolute`（旋转）/ `prismatic`（平移）/ `fixed` |
| **axis** | 运动轴向 | `x` / `y` / `z`（parent-local 坐标系） |
| **origin** | 旋转中心坐标 | `{x, y, z}`（parent-local） |
| **parent** | 运动跟随谁 | 场景树中的某个父级节点 |
| **role** | 语义角色（供 AI 生 PKF 按意图匹配） | 车体前进 / 门架升降 / 叉齿旋转 / 夹爪开合 ... |

一个典型模型（三向叉车）要配 5 个关节，每个关节填 5 个字段。外行做不了。

## 3. 关键技术观察（决定 AI 的 scope）

MotionForge 的关节驱动数学暴露了一个重要差异：

**Revolute（旋转）**：
```
child 位置 = origin + Rotation(axis, value) · (baseTransform.position - origin)
                ↑ origin 必须精确
```
origin 就是铰链轴位置，偏一毫米 → 旋转时零件扫出错误弧线 → 视觉明显不对。

**Prismatic（平移）**：
```
child 位置 = baseTransform.position + axis · value
                                        ↑ 只看方向
```
**origin 不参与计算**。prismatic 的 origin 写 (0,0,0) 都能跑，只要 axis 方向对。

### 由此得到 AI 打关节的难度地图（按我们实际关节分布加权）

| 要算什么 | 难度 | 在我们模型里的权重 | 当前优先级 |
|---|---|---|---|
| **父子拓扑** | ⭐⭐⭐⭐ | 每个关节都要 | 🔴 **最高** |
| prismatic 的 axis | ⭐⭐ | 80%+ 关节需要 | 🔴 高 |
| type 分类（prismatic/revolute） | ⭐⭐ | 每个关节都要（但大多 prismatic） | 🟡 中 |
| revolute 的 origin | ⭐⭐⭐⭐ | <20% 关节需要 | 🟢 基础研究，不赶工 |
| revolute 的 axis | ⭐⭐⭐ | 同上 | 🟢 同上 |
| prismatic 的 origin | ⭐ | 无关（数学上不参与） | ⬜ 写死 (0,0,0) |

**对比之前的版本**：原来的难度地图把 revolute origin 当核心硬骨头，那是假设 revolute 占比不小。我们实际场景下 prismatic 占主导，**父子拓扑成为真正的瓶颈**——父子错了链式动画断，prismatic 无法驱动，MotionForge 的[历史 bug](#) 也多次踩在这上面。

## 4. 我们当前的方向（待你验证/补充）

**技术分工**（按当前模型分布重新排序）：

```
AI（LLM + 几何分析）：
  - 父子拓扑推算（最关键！）
  - prismatic axis 方向判断（3 选 1）
  - type 分类（prismatic vs revolute）
  - 识别哪些零件是可动的
  - [基础研究]revolute origin 精确定位 — 继续推进但不赶工

规则 / 几何算法：
  - 父子拓扑的几何兜底（bbox 包含 / 距离，跳过无名 Object3D 包装）
  - prismatic axis 默认值（bbox 主轴 / 父级朝向 / 命名语义）

用户：
  - 一次性确认 UI（不逐个配，只"看起来对"即可）
  - 不满意时可手动调单个关节
```

**核心假设（修订版）**：
- **当前阶段核心**：父子拓扑 + prismatic axis，搞定这两块能覆盖 80%+ 场景
- **基础研究**：revolute origin 的几何算法（圆柱面拟合 / 接触面检测）继续推进，但属于"厚积薄发"的基础设施，不是当前演示/落地的瓶颈
- **对齐产品目标**："不懂机械的人也能用"——只要父子关系和轴向对了，用户确认时看到动画正确就够

## 5. 需要你研究/补充的开放问题（按当前优先级排序）

### 🔴 Q1（最高优先级）. 父子拓扑怎么自动推？

这是我们实际场景下最关键的问题。候选：
- BBox 包含关系（A 被 B 包含 → A 是 B 的子级）
- 最近距离（A 离 B 最近 → A 挂 B 下）
- 几何接触面分析
- LLM 从场景树 + 命名推断

**坑（必看）**：GLTFLoader 导入 GLB 时会在逻辑父级外面插入无名 `Object3D` group。如果直接取 `mesh.parent`，拿到的是无名包装，MotionForge 的链式动画会断。**必须跳到"第一个有名字的祖先"**。

你研究过哪些方案？哪种在多候选父级有歧义时（如叉齿既包含在门架又包含在升降组）表现最稳？

### 🔴 Q2（高优先级）. prismatic 的 axis 怎么判断？

80%+ 关节都是 prismatic，这个直接决定动画方向对不对。候选：
- (a) 主惯性轴（长条零件沿长边滑）
- (b) 父级坐标系主轴
- (c) LLM 按零件名称推断
- (d) 默认 Y 轴，让用户改

实际场景下哪种命中率最高？多种方法 ensemble 能不能进一步提升？

### 🟢 Q3（基础研究，不赶工）. revolute 的 origin 怎么精确定位？

少量关节需要，长期重要但**不是当前阶段瓶颈**。候选：
- BBox 细长轴端点（铰链一般在细长零件的端头）
- 与父级接触面的中心（圆柱面拟合）
- 零件轴对称的对称轴
- LLM + 多视图渲染 + 视觉推断

你可以继续研究这块作为基础，但不需要为当前演示/GT 评估赶工。

### 🟡 Q4. 用户确认 UI 的粒度

- 全局预览（类似 URDF viewer，一次看所有关节，打勾确认）
- 逐关节确认（一次一个，点"对"或"改"）

哪种对不懂机械的人更友好？你有类似产品的参考吗？

### 🟡 Q5. 失败回退路径

AI 打错时，理想的 UX 是什么？
- 用户手动改某个关节 → AI 其他保留
- 整体重跑（给不同 prompt）
- 完全回退到手动配

### 评估维度的权重建议

GT 标注和 evaluator 的评分权重应该反映实际模型分布：

| 维度 | 权重 |
|---|---|
| 父子拓扑准确率 | 最高 |
| axis 准确率（尤其 prismatic） | 高 |
| type 准确率 | 高 |
| role 准确率 | 中（看是否评语义匹配） |
| **origin 精度** | 跳过（GT origin mode = approximate） |

GT 标注只需 `child / parent / type / axis` 必填，origin 全部写 (0,0,0)，revolute 少数关节肉眼拖一下即可。

### MotionForge 接入契约

AI 打关节只要吐出这个 schema 的 JSON 数组，MotionForge 就能直接消费：

```json
[
  {
    "name": "_CS19110",               // 零件在场景树里的名字
    "type": "revolute",               // revolute / prismatic / fixed
    "axis": "z",                       // x / y / z (parent-local)
    "origin": { "x": 0, "y": 0, "z": 0 },  // parent-local（revolute 必须精确）
    "parent_name": "门架组件",        // 逻辑父级（跳过无名包装）
    "role": "叉齿旋转"                // 语义标签（AI 可用 LLM 打，也可默认空让用户填）
  },
  ...
]
```

符合这个 schema，后续"自然语言生 PKF → 动画"全自动，不需要动 MotionForge 代码。
