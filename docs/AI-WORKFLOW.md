> 作者：Hockwang

> 阅读时间：约 12 分钟
> 适合谁：已经会用基础功能（加载模型、配关节、打关键帧），想用 **AI + 模板 + 可视化调试** 把工作流跑顺的人

## 这是什么 / 不是什么

基础版 USER-GUIDE 教你怎么"用键盘鼠标手工做动画"。这篇教你怎么**让 AI 把大部分枯燥活干掉**，你只负责：

1. 把关节和 role 配清楚（一次性投入，5-10 分钟）
2. 用自然语言 / 模板触发 AI 生成
3. 看轨迹 overlay 判断哪里不对
4. 用精确的"偏差数字"喂回给 AI 或手动微调

**不是**全自动黑盒，不是一句"做一个取货动画"就能完美出片的工具。是**人 + AI + 可视化反馈** 三者在一个闭环里轮替，比纯手工快 5-10 倍，比盲信 AI 靠谱得多。

## 三种生成路径，怎么选

编辑器里做动画有三条路径。实际使用时 80% 走路径 1 或 2：

| 路径 | 按钮 | 适合场景 | 限制 |
|------|------|---------|------|
| **模板路径**（叉车 / 三向车）| 🚀 一键 → 弹窗选"用模板" | 叉车 / 三向车取放货的**标准流程** | 只支持内置几种模板（forklift / threeway） |
| **AI 自由生成** | 🚀 一键 → 弹窗选"自由生成" | 非标准动作（柜门开关 / 机械臂挥手 / 旋转展示…） | AI 要自己推理几何，偶尔会瞎编参数 |
| **关键帧手工** | 时间轴 "添加关键帧" | 想精确控制每一帧 / 给 AI 做不出来的兜底 | 慢，改一次动作幅度要全重调 |

**决策逻辑**：
- 叉车 / 三向车取放货 → **模板路径**（最稳，前端锁死几何，AI 只管节奏）
- 其他场景 → **AI 自由生成**（试第一次）
- AI 反复调不对 → 切关键帧手工

## 1. 前置：关节和 role 标对（杠杆点）

这一步决定了后面 AI 能多顺。5 分钟的功夫能省后面 30 分钟的来回。

### 1.1 role 不是自由填空

role 字段看起来可以自由输入，但 **AI 按 role 做语义匹配**。你写什么它就照什么匹配：

| 你填的 role | AI 看到的意义 | 结果 |
|-----------|--------------|------|
| `门架升降` | "这个关节负责升降" | "叉齿抬高 0.6m" 正确命中 |
| `prismatic_z_joint` | "这是个 z 轴平移" | "叉齿抬高" → AI 可能选对也可能选错（靠猜） |
| `零件A_向上` | 无语义 | AI 只能按名字模糊匹配，出错率高 |
| （空） | 完全不知道 | 只能按 axis 猜，概率 50-50 |

**建议**：用下拉里的**标准词汇**（门架升降 / 叉齿旋转 / 叉齿侧移 / 车体前进 / 车体横移 / 门架横移），别自己发明。

### 1.2 标准 role 词表（当前支持）

| role | 典型零件 | 类型 | 说明 |
|------|---------|------|------|
| 车体前进 | 整车 / 底盘 | prismatic | 前后方向行进 |
| 车体横移 | 整车横向（少见） | prismatic | 侧向移动 |
| 门架升降 | 门架 / 升降柱 | prismatic | 上下升降 |
| 门架横移 | 门架侧移机构 | prismatic | 门架左右 |
| 叉齿侧移 | fork carriage | prismatic | 叉齿侧向 |
| 叉齿旋转 | fork 旋转轴 | revolute | 三向车的旋转轴 |

不在表里的动作（柜门、机械臂等）用"其他"手动输入，但命中率会降。

### 1.3 双段门架的特殊配法

如果叉车有**内外两段门架**（内门架在外门架里滑动），两段都是"门架升降"，还需要配 **limit_upper + overflow_to**：

- 在内门架关节的配置面板里：`limit_upper` 填内段上限（比如 1.5m）、`overflow_to` 填外门架的**零件名**（比如 `OuterMast`）
- 其他都按普通关节配

运行时：内门架吃不下的部分自动转给外门架。见 [§8](#8-进阶双段门架-overflow)。

## 2. 场景 markers：告诉 AI "取哪放哪"

AI 不知道货物在哪、要放哪。你要**在 3D 场景里放 3 个标记**：

### 2.1 添加 markers

右侧面板"场景标记"区域：

| 按钮 | 作用 | 类型 |
|------|------|------|
| "添加 cargo" | 放一个货物占位框 | cargo（带 w/h/d 尺寸） |
| "添加 pickup" | 标取货起点 | pickup |
| "添加 drop" | 标放货目标 | drop |

点按钮后，marker 出现在场景中央。拖动 + 改坐标把它摆到正确位置。

### 2.2 cargo 的尺寸要填对

cargo 是货物占位框，AI / 模板用它的尺寸算"叉齿要插多深 / 要抬多高"。比如 1m³ 的箱子：

```
size: { w: 1.0, h: 1.0, d: 1.0 }  // 宽 高 深（米）
```

尺寸瞎填，AI 就算瞎了。

### 2.3 pickup / drop 位置

- **pickup**：cargo 现在在哪儿（对叉车来说就是 cargo 标记的脚下）
- **drop**：cargo 要送到哪儿（目标货架 / 地面位置）

模板路径 + AI 都从这两个 marker 读坐标，不用你在 prompt 里说"到 3.5 米前方"。

## 3. 🚀 一键流程

时间轴上方有个 🚀 一键按钮，这是**最推荐的入口**。流程：

```
点 🚀 一键
  ↓
检测模板：模型里有"叉齿旋转"+"门架升降"+"车体前进" → 三向车模板命中
  ↓
弹窗问："检测到【三向车】模板，用模板还是自由生成？"
  ↓
选"用模板" → 进模板路径（§4）
选"自由生成" → 进 AI 自由路径（§5）
  ↓
两条路径最终都会：生成 PKF → 自动切到 PKF 播放 → 你按播放看效果
```

没检测到任何模板（比如机械臂 / 柜门）→ 直接走自由生成。

## 4. 模板路径（叉车 17 段 / 三向车动态段）

### 4.1 模板是什么

模板 = **前端写死的"取放货该怎么走"脚本**。几何参数（从 pickup 走到 cargo 的精确距离、叉齿要插多深、什么时候升到多高）全在前端算，AI **只负责节奏**（比如"整体 10 秒 / 20 秒"、"走快点 / 走慢点"）。

**好处**：结构性瞬移 bug（叉齿突然飞到 cargo 位置）**零概率**出现，因为几何不是 AI 算的。

### 4.2 两种模板

| 模板 | 触发条件 | 段数 |
|------|---------|------|
| **ForkliftTemplate**（叉车） | 检测到门架升降 + 车体前进 role | 17 段（固定） |
| **ThreewayTemplate**（三向车 VNA） | 额外检测到叉齿旋转 role | 13-22 段（按目标方向动态） |

三向车会根据 drop 方向自动决定要不要旋转叉齿 90° / 180°。

### 4.3 用模板

点 🚀 一键后选"用模板"：

1. 弹输入框让你输入"节奏意图"（选填）：
   - 空：用默认节奏（均衡 ~20 秒）
   - "快一点"：总时长减少，每段缩短
   - "要求取货平稳放货快"：分段速率不同
2. 自动编译出 PKF，应用到时间轴
3. 切 PKF 驱动播放
4. 按播放看

### 4.4 看是否合理

**放完立即看两件事**：

1. 打开 🎨 轨迹 toggle，查 console.table —— 每段 fork 和 cargo 的世界坐标应该和你期望一致
2. 按播放 → 看有没有瞬移（cargo 突然从地面飞到 fork 上）

模板路径的 PKF 基本不会有瞬移。出问题通常是 marker 位置或 cargo 尺寸没配对。

## 5. AI 自由生成路径

> 基础的 AI 面板操作（点按钮、输入文字、点生成、应用）见 [USER-GUIDE §5](USER-GUIDE.md#5-用-ai-自然语言做动画推荐)。本章只补"进阶怎么用"：**写 prompt 的原则、常见 AI 错误类型、怎么定位偏差**。

### 5.1 什么时候用

- 模型不是叉车 / 三向车（柜门、机械臂、AGV、设备展示等）
- 动作不是标准取放货（旋转展示、开合、挥舞等）

### 5.2 写好输入的几条原则

**好的输入**：
```
叉齿旋转 45 度，门架抬升 0.6 米
```

**不好的输入**：
```
做一个漂亮的取货动画    ← 太空
零件 A 往那边动一下     ← 没有数字
把所有能动的都动一下     ← AI 会瞎编
```

**更好的输入**（精确到关节）：
```
@_CS19110 旋转 30 度，@cAR201 升到 1.2m
```

`@` 引用可用关节 chips。会精确绑关节，不走 role 匹配。

### 5.3 如果 AI 说"找不到对应角色"

AI 会返回一个错误 + 列出当前模型里**有哪些 role**：

```
error: 当前模型没有"车体前进"角色的关节
available_roles: ["门架升降", "叉齿旋转", ...]
```

两种修法：

- 用它列出来的 role 词改你的输入（"车体前进" → 改成"门架升降"）
- 或去关节配置面板，给某个关节补上"车体前进"的 role 字段

### 5.4 AI 出错的常见类型

| 症状 | 成因 | 修法 |
|------|------|------|
| cargo attach 瞬间飞 | AI 没覆盖某个维度（通常是 y 或 z） | `ensurePkfCoversAttachPoint` 会自动补救，看 warnings；还不行就手动加 step |
| 动作幅度全错 | AI 把 `approach_gap` 填成非 0 | 系统自动 sanitize 为 0，看 warnings 确认 |
| 选错关节 | role 没配 / 配错 | 去关节面板补 role |

## 6. 🎨 轨迹 overlay：你的调试眼睛

### 6.1 打开

时间轴右侧找 🎨 轨迹 toggle，勾上。

### 6.2 看什么

3D 视口里会出现：

| 颜色 | 含义 |
|------|------|
| 🔵 蓝线 | fork（叉齿承载面）的完整轨迹 |
| 🟠 橙线 | cargo（货物底面）的完整轨迹 |
| 🔵 蓝小球 | 每段 PKF step t_end 时 fork 的位置 |
| 🟠 橙小球 | 每段 PKF step t_end 时 cargo 的位置 |
| 🔴 红大球 | attach 事件（取货瞬间）|
| 🟢 绿大球 | detach 事件（放货瞬间）|

### 6.3 Console.table 比视觉更精准

打开浏览器 Console（F12），勾 🎨 toggle 后会自动打印一张表：

```
seg | name              | joint     | t_end | fork(threejs)        | cargo(threejs)       | cargo-fork.dy
----+-------------------+-----------+-------+----------------------+----------------------+-------------
 1  | 车体前进到 cargo  | _AHR23    | 1.500 | (0.48, 0.04, 1.00)   | (1.50, 0.50, 1.00)   | 0.46
 2  | 门架升到取货高度  | cAR201    | 2.500 | (0.54, 0.40, 1.00)   | (1.50, 0.50, 1.00)   | 0.10
 ...
```

这张表是**精确到 mm 的动画切片**。调试时盯这个比盯视觉靠谱得多。

后面紧跟一行 Y 范围汇总：

```
fork.y : [0.042, 1.000] 变化 0.958m
cargo.y : [0.500, 1.098] 变化 0.598m
```

如果"变化 0.958m"但视觉看着平 → 相机透视压缩，按数字键 3 切正射视图看。

### 6.4 视角压缩陷阱

轨迹线在侧视图里经常"看着像水平线"，但数据显示 Y 方向有 1m 变化。这是**相机透视**的错觉，不是 bug。两个解法：

- **切正射视图**：视口右上角 gizmo 点击 "+Z / -Z / +X / -X" 切正射，Y 变化会完全展开
- **看 console.table 数字**：`fork(threejs)` 那列的 y 值，直接比对，不靠眼睛

## 7. 与 AI 协作修 bug 的正确姿势

这是整篇指南的核心。动画出问题时，**怎么让 AI（我 / GPT / 其他协作者）快速帮你定位**决定了效率。

### 7.1 不好的协作方式

> "叉齿动作不对，帮我看看"

AI 看不到你的屏幕，只有你截图给的一张图。截图里没有坐标轴、没有刻度、看不出来哪不对。来回拉扯 3-5 轮才能定位问题。

### 7.2 好的协作方式

提供**三件东西**的组合：

1. **一张 🎨 轨迹开了的截图**（最好切到正射视图）
2. **Console.table 的完整文字**（复制粘贴）
3. **一句精确描述**："seg 12 的 cargo 应该落在 x=-1.5 y=1.0，实际在 x=-1.48 y=1.1，偏差 y=+0.1m"

AI 拿到这三件东西几乎一次就能定位问题（公式算错 / 参数填错 / 关节 role 绑错）。

### 7.3 模板问题 / free AI 问题

**模板生成后出偏差**：
- 首先检查 cargo / drop marker 的坐标有没有摆对
- 检查 cargo 尺寸 w/h/d 填对了没
- 如果 marker 和尺寸都对 → 可能是模板本身的 bug（填 GitHub issue）

**AI 自由生成后出偏差**：
- 看 console.table 找到偏的那段
- 打开右侧 PKF 步骤面板，找到对应 step，看公式
- 手动改公式或重跑 AI with 更精确的 prompt

### 7.4 诊断神器 `__mf`

浏览器 Console 里几个调试钩子：

```js
__mf.lastOneshot         // 最后一次 🚀 AI 请求 / 响应
__mf.lastTemplate        // 最后一次模板编译结果
__mf.trajectoryOverlay   // 轨迹 overlay 对象
__mf.getJointDefs()      // 所有关节定义
__mf.keyframeManager.pkfSteps   // 当前 PKF 步骤
```

出了怪事都先 `console.log(__mf.lastOneshot)` 看 AI 到底返回了什么，常常能省一半 debug 时间。

## 8. 进阶：双段门架 overflow

叉车门架是内外嵌套结构的常见场景。**两段都是门架升降**，不能只用一个关节。

### 8.1 配法

以 `InnerMast` 嵌在 `OuterMast` 里为例：

| 字段 | InnerMast | OuterMast |
|------|-----------|-----------|
| 类型 | prismatic | prismatic |
| 轴向 | z | z |
| role | 门架升降 | 门架升降 |
| limits.max | 2.0 | 1.0 |
| **limit_upper** | **1.5** | null |
| **overflow_to** | **OuterMast** | null |

### 8.2 运行时行为

模板 / AI 输出一个"升到 1.8m"的 value：

```
InnerMast value = 1.8
  ↓
  _redistributeOverflows 跑：
  1.8 > limit_upper (1.5) → 溢出 0.3
  InnerMast 值 clamp 到 1.5
  OuterMast value += 0.3
  ↓
最终：InnerMast=1.5，OuterMast=0.3
视觉：内段升 1.5m，外段再升 0.3m，总高 1.8m ✓
```

`findPrimaryByRole('门架升降')` 会自动把 OuterMast 当 slave（因为它被 InnerMast `overflow_to` 指向），不参与 primary 选择。你**不用标 primary/slave**，规则自动推导。

### 8.3 验证

拖 InnerMast 的 value 滑块，超过 1.5 后应该看到 OuterMast 也跟着升。没跟就是 `overflow_to` 名字写错了（要填 OuterMast 的**零件名**，不是 id）。

## 9. 导出的 ZIP 下游怎么消费

对接下游系统（仿真 / 中台 / 其他 3D 软件）时，导出的 ZIP 就是**交付契约**。

### 9.1 ZIP 里有什么

```
{name}-motion-package-{timestamp}.zip
├── manifest-{ts}.json   — 版本号 + 文件索引 + scene markers 元数据
├── model-{ts}.glb       — 零位态的场景
├── joints-{ts}.json     — FK 关节定义（含 role、parent_name、overflow）
├── motion-{ts}.json     — 全局 clips + 关键帧 + reparent 事件
└── pkf-{ts}.json        — PKF 参数 + 步骤（可选）
```

### 9.2 下游要看的字段

- **manifest.schema_version**：必须 **7**（当前版本）。下游按这个版本号分派解析逻辑
- **joints[].name** / **parent_name**：跨 roundtrip 稳定的标识，别用 uuid
- **joints[].role**：业务语义，下游 AI / 映射规则靠这个
- **motion.clips[].reparent_events**：attach / detach 时刻和目标
- **pkf.steps[].joint**（关节 name）：PKF 公式绑的关节
- **manifest.scene_markers**：cargo / pickup / drop 元数据

完整字段定义见 [docs/schema/v7.md](schema/v7.md)。

### 9.3 下游集成建议

1. 按 `schema_version` switch case 做版本兼容（v4 / v5 / v6 / v7 都可能遇到）
2. 主键用 **name**，不用 uuid（uuid 每次加载重生成）
3. 新字段用 `?? null` 安全读取（老 ZIP 可能缺 v6 / v7 字段）
4. GLB 模型是零位态的，下游自己根据 joints + motion 驱动

## 10. 常见问题

### Q: 🚀 一键没检测到模板，直接走自由生成，但我明明有叉车模型

检查三件事：

1. 有没有 cargo / pickup / drop 三个 marker？没有模板拒绝编译
2. 有没有 role=门架升降 + role=车体前进 的关节？缺一个就不命中
3. 有没有 attach 事件（即某个 reparent_event 里 `new_parent_name` 非空）？没有也不命中

在 console 跑 `__mf.lastTemplate` 看 `missing` 字段，会告诉你缺什么。

### Q: 模板路径生成后，动画里叉齿瞬移到 cargo 上

模板路径**理论上不会瞬移**。如果发生：

1. 检查 cargo marker 的 3D 位置（拖它看、或 console 查 `cargo.getWorldPosition()`）—— 很可能放错了地方
2. 检查 cargo 的 size 字段（w/h/d）—— 填错了会让模板算错插入深度

### Q: AI 自由生成后 attach 瞬间 cargo 飞了 0.3m

`ensurePkfCoversAttachPoint` 会自动检测并补救，看 console warnings：

```
🔧 自动补 z 方向 step: Mast 0→0.3（AI 漏写；attach 前已到位）
```

如果没补救 warning 但还是飞，说明是公式算错了，不是缺维度。打开 PKF 步骤面板找 attach 前最后一段的 value_end，手动改。

### Q: 轨迹看起来不贴叉齿 tine

**可能 A**：视角压缩。看 console.table 里 fork.y 的变化范围，如果有 1m 变化但视觉看着平 → 切正射视图。

**可能 B**：fork 对应的 Object3D（`_CS19110` 或类似）的 bbox 不覆盖 tine 几何（建模问题）。这种情况只能让建模师修模型。

### Q: 导入一个老的 v4 ZIP 报错

v4 → v7 有几个破坏性变化：

- v4 的 motion.json 可能是 per-object channels schema（老格式），导入时会提示"忽略关键帧数据"
- v4 没有 reparent_events / scene_markers / pkf，这些字段缺失不影响，系统会按缺失处理

如果连模型都加载不出来 —— 多半是 GLB 文件坏了，不是 schema 问题。

### Q: 我想给 AI 一个更精确的"修这段"指令

把 console.table 的**那一段那一行**复制出来，配合一句话描述：

> "seg 12 的 cargo 应该落在 (-1.5, 1.0, 5.5)，实际 (-1.48, 1.098, 5.532)，我想让它准确到 ±1cm"

AI 能直接改对应 PKF 步骤的公式。不用来回猜。

### Q: __mf.lastOneshot 是什么

最后一次 🚀 一键生成的 **完整 AI 请求 / 响应快照**：

```js
{
  intent: "从 A 点取货送到 B 点",
  scene: [...],        // 传给 AI 的场景对象列表
  joints: [...],       // 传给 AI 的关节定义
  l1: { rows, reparent_events, warnings },   // L1 返回
  l2: { parameters, steps },                 // L2 返回（原版）
  l2Patched: { ... },  // 经过 ensurePkfCoversAttachPoint 修补后的
}
```

出问题时 `console.log(__mf.lastOneshot)` 能直接看 AI 接收/返回了什么，省下大半 debug 时间。

## 结语

核心就两件事：

1. **前期把 role 和 markers 标清楚**（5 分钟投入）
2. **出问题时用 🎨 轨迹 + console.table 做精确描述**（不是模糊地说"不对"）

把这两件做到位，AI 协作的效率会从"来回拉扯 5-10 轮"降到"一次或两次命中"。
